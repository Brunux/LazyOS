# 2026-10-28 - spec 016, a local model on this machine

Run on the Hayato, like the reports before it: the question is a fact about this
SoC's four big cores and four little ones, its 3.8 GB of RAM, and about what
`llama.cpp` does with a default flag - and none of that can be answered inside a
chroot.

## What was exercised

`specs/016-local-models.md` - the measured flag set, `~/.config/bin/lazyos-model`
(the wrapper), `~/.config/lazyos/models.sha256` (the pins), the three surfaces
(`Alt+Ctrl+M`, the root menu's *Local model* row, `org.lazyos.model.desktop`),
`config.d/34-local-model.conf`, and the three witnesses.

## The machine and the binary

| | |
|---|---|
| CPU | 4x Cortex-A76 + 4x Cortex-A55 (`nproc` 8) |
| RAM | `MemTotal` 3805 MiB, `MemAvailable` 2613 MiB with the session up - the 4k-context KV cache is most of what is left over |
| GPU compute | none that `llama.cpp` can use: Panfrost is OpenGL 3.1, PanVK answers *Mali-G57 not supported* |
| package | `llama.cpp-examples 1:0.7.0+dfsg-2`, `libggml0 0.27.0-1` |
| `llama-cli --version` | `version: 0.7.0 (build 11669, commit Debian)`, `built with GNU 16.2.0 for Linux aarch64` |
| backends | `/usr/lib/aarch64-linux-gnu/ggml/backends0/libggml-cpu-armv8.2_2.so` (1867 `sdot`), runtime-dispatched |
| models | `qwen3-1.7b-Q4_0.gguf` 1 231 813 024 B, `qwen3-1.7b-Q4_K_M.gguf` 1 282 439 584 B |

The package is the binary, and that is a measurement rather than a preference: a
platform build (`-DGGML_CPU_ARM_ARCH=armv8.2-a+dotprod+fp16`, `-DGGML_OPENMP=OFF`,
thin LTO) took **396 s** and measured **11.14 tok/s** against the package's
**10.95** at correct settings. `tools/llama.cpp/` therefore does not exist.

## The four flags, and what losing each one costs

| setting | measured | what it means |
|---|---|---|
| `llama-cli` with no `-t` | **6.67 tok/s** | llama.cpp asks for `nproc` (8); the A55 cluster is 7.8x slower per core and drags every barrier |
| `-t 4` | **11.19 tok/s** | the A76 cluster alone |
| `-t 8` with a local `-DGGML_OPENMP=OFF` build | 9.98 tok/s | so the cliff is the package's OpenMP pool as much as the hardware |
| Q4_K_M, 1800-token prompt | 46.16 tok/s prefill, **49 s** to first token | |
| **Q4_0**, same prompt | 84.66 tok/s prefill, **31 s** to first token | repacked dotprod kernels; 1.14 GiB against 1.19 |
| f16 KV at 4k context | 2584 MiB peak RSS | does not fit beside a browser |
| **`-fa on -ctk/-ctv q8_0`** | **2356 MiB** peak RSS | 228 MiB, i.e. the difference between fitting and swapping |

Per-core compute, from `llama-bench` (GMAC/s, `-p 512 -n 0`):

| threads | A76 cluster | A55 cluster | unpinned |
|---|---|---|---|
| 1 | 31.9 | 4.1 | - |
| 4 | 103.5 | 15.7 | - |
| 8 | - | - | **66.8** (slower than four) |

Things that were measured and **not** shipped: `-b 256 -ub 128` (2358 MiB, inside
noise) and a smaller `-c` (the floor is the 1280 MiB of weights). `taskset -c 4-7`
is kept and buys nothing (11.19 unpinned against 11.14 pinned): it keeps the
desktop off the big cores, and it is skipped when `nproc` is under 8.

## Through the wrapper

```
$ ~/.config/bin/lazyos-model --flags

$ ~/.config/bin/lazyos-model qwen3-1.7b-Q4_0 -st -n 16 -p "one word: hello"
[ Prompt: 80.9 t/s | Generation: 11.2 t/s ]

$ ~/.config/bin/lazyos-model qwen3-1.7b-Q4_0 -st -n 40 -p "Name three fruits, one line."
Apple, banana, orange.

[ Prompt: 70.0 t/s | Generation: 10.5 t/s ]
```

11.2 and 10.5 tok/s against the default's 6.67, which is the whole point of the
wrapper: the number is not a property of the machine, it is a property of four
flags.

## The window, and the dead key it nearly was

`swaymsg -t get_tree`, after `swaymsg exec -- 'lazyos-model qwen3-1.7b-Q4_0'`:

```
app_id=lazyos-model float=user_on rect=997x696 at 183,123
```

`for_window [app_id="lazyos-model"]` from `config.d/34-local-model.conf` resizes
to 1000x700 and centres, and foot's own client-side decoration takes the 3 px:
**997x696 on the 1366x912 panel**, which is what the earlier hand test read.

The first version of `window()` tested `[ -t 0 ]` to decide whether it already had
a terminal, and under the key it did: **sway's `exec` inherits the VT the
compositor was started on** (`/proc/$(pgrep -x sway)/fd/0 -> /dev/tty7`), so the
script believed it was running in a terminal, skipped `foot`, and started
`llama-cli` with no window - the model waiting on a VT nobody was looking at,
which reads exactly like a key that does nothing. This is the trap `lazyos-profile`
already documents for `rofi-dev`, in a second script. The predicate is now the
same one (`on_terminal`: a tty *and* this process is its foreground group,
`ps -o tpgid=` equal to `ps -o pgid=`), and both directions were exercised:

| launch | result |
|---|---|
| `swaymsg exec -- 'lazyos-model qwen3-1.7b-Q4_0'` (the key's path) | one `foot`, `app_id=lazyos-model`, floated 997x696 |
| `script -qec 'lazyos-model qwen3-1.7b-Q4_0 ...' /dev/null` (a real pty) | no window; it runs in place, 11.2 tok/s |
| `HOME=... WAYLAND_DISPLAY= lazyos-model --fetch` with a stub `curl` | no window; the download prints its progress on the terminal |

## `--fetch`: the file is pinned or it does not exist

The real download is 1.2 GB, so the path was exercised against a fixture and a
stub `curl` in a throwaway `$HOME`, with the pins file naming the fixture's hash:

```
--- good pin ---
Fetching qwen3-1.7b-Q4_0.gguf
  from https://huggingface.co/bartowski/Qwen_Qwen3-1.7B-GGUF/resolve/main/Qwen_Qwen3-1.7B-Q4_0.gguf

/tmp/opencode/fm/home/.local/share/lazyos/models/qwen3-1.7b-Q4_0.gguf.part: OK

ready: /tmp/opencode/fm/home/.local/share/lazyos/models/qwen3-1.7b-Q4_0.gguf
rc=0

--- a pin that does not match ---
/tmp/opencode/fm/home/.local/share/lazyos/models/qwen3-1.7b-Q4_0.gguf.part: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
lazyos-model: checksum mismatch - not keeping the file
rc=1
files left: 0
```

An address with no pin is refused before anything is downloaded at all
(`qwen3-1.7b-Q5_K_M is not pinned in .../models.sha256`, rc=1), because a file
whose hash nobody recorded is a file of unknown provenance.

The two files that are here match `~/.config/lazyos/models.sha256`:

```
$ ~/.config/bin/lazyos-model --verify
qwen3-1.7b-Q4_0.gguf: OK
qwen3-1.7b-Q4_K_M.gguf: OK
```

`--list` prints the models that are here, and names a pinned one that is not
(`not downloaded: <file> (lazyos-model --fetch <name>)`) so the row is
discoverable instead of an empty menu:

```
qwen3-1.7b-Q4_0
qwen3-1.7b-Q4_K_M
```

## Exit codes

The shell's contract, exercised under `dash`:

| invocation | code | meaning |
|---|---|---|
| `--help` | 0 | usage |
| `--flags`, `--list`, `--verify` | 0 | it answered |
| `--nope` | 2 | usage |
| `nosuch` | 2 | no such model |
| no model at all | 3 | nothing to run with, card shown |
| `Escape` in the `fzf` picker (several models, no argument) | 1 | cancelled, nothing happened |
| `--fetch` with a bad pin | 1 | refused, nothing kept |

## What the witness answers

`scripts/check-system.sh` against this branch on the device:

```
  OK    local model ready (Alt+Ctrl+M, the root menu row, the launcher entry and its icon)
  OK    the model runs on four threads (the A76 cluster)
  OK    the model's KV cache is q8_0 behind flash attention (4k context fits next to the session)
  OK    the local model matches its pinned SHA256 (2 file(s))
```

The failure direction matters more than the passing one, so it was exercised too,
with a `$HOME` that has no wrapper and no pins:

```
  FAIL  local model incomplete: bin/lazyos-model(not executable) .config/lazyos/models.sha256(pins) bar-menu(no-row) (the key does nothing, or the launcher row has a hole)
  SKIP  no local model yet: 'lazyos-model --fetch' downloads Qwen3-1.7B (1.2 GB), checked against its pin
```

and the flags direction is a separate pair of lines, because a wrapper edited
back to `-t 8` is not broken - it is 40 % slower, and no other check would notice.

`sway -C -c /etc/sway/config` exits 0 with `34-local-model.conf` included, which
is the one way to validate a drop-in (`swaymsg -t get_config` does not expand
includes).

## What is deliberately not here

- **The weights.** 2.4 GB for the two measured files, a third of the disk, and
  stale the moment a better 1.7B appears. They are fetched into
  `~/.local/share/lazyos/models/`, which a rebuilt image keeps.
- **A vendored `tools/llama.cpp/`.** +1.7 % for 396 s of build, measured.
- **A server or a daemon.** One `llama-cli` while the window is open; nothing
  answers a socket and nothing survives the window.
- **`ollama`.** Installed on this machine outside every package list; it inherits
  `nproc` and therefore sits in the 6.67 tok/s regime unless it is given
  `num_thread 4`. This spec does not manage it.
