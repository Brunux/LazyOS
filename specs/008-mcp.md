# Spec 008 — `lazyos mcp`: the desktop the agent can drive

- **Status**: approved (2026-10-29: power, format and swap keep the propose tier, and a propose
  tool opens the real gated window rather than a card of its own)
- **Phase**: 2
- **Depends on**: 001, 004, 005, 007
- **Model**: `claude-opus-5-5` (effort `xhigh`) — a protocol surface plus a permission model
  whose mistakes are destructive; the manifest is a security boundary, and the cost of a wrong
  tier is a power-off nobody confirmed. Fallback `claude-fable-5-1`: a re-route goes up a tier
  here, never down.
- **Branch**: `spec/008-mcp`
- **Plan**: [`docs/plan-ui.md`](../docs/plan-ui.md) §13 (AI in the loop), §13.3 (tiers),
  §15 (witnesses)
- **Old paths**: none; this is the new surface `opencode` calls

## Problem

The desktop has no machine-readable surface. An agent can run shell commands but cannot see
the screen, cannot ask a `lazyos` command to show a result to the person, and cannot tell a
safe action from a destructive one. The plan's contract is: the AI **proposes**, the person
**confirms**, and the manifest proves it.

## Scope

**In (`lazyos mcp` + `lazyos-mcp` crate):**

- **Server**: JSON-RPC 2.0 over stdio (MCP), one process per client session, no listening
  socket. `initialize`, `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/read`,
  `prompts/list`.
- **Tools, four tiers**. Names use `_`, not `.`: the model providers' tool-name rule is
  `[A-Za-z0-9_-]`, and a client that passes an MCP name through unchanged would send the
  provider a name it rejects.
  - *read*: `desktop_status`, `desktop_screenshot` (grim to a temp path, returns the path),
    `desktop_windows`, `theme_current`, `packages_installed`, `system_report` (the
    check-system data), `clipboard_read`, `task_list`.
  - *act*: `menu_open` (the root menu or the palette, optionally with a filter typed in),
    `task_open` / `task_stop` (stop only a task whose record says it is stoppable),
    `theme_set`, `notify_send` (rate-capped), `view_open` (a file or directory through
    `lazyos-view`).
  - *propose*: `install_propose`, `format_propose`, `swap_propose`, `power_propose` — each
    **opens the real, already-gated window** the menu opens (`rofi-install`, `rofi-format`,
    `rofi-swap`, and the root menu's Power confirm with Cancel selected) and returns
    "proposed"; it executes nothing, and the gate (the typed disk name, the disk list, the
    second answer) is the person's and is never seen by the AI.
  - *refuse*: never exposed. The list is in the spec: `run` (arbitrary shell), `format_apply`,
    `install_apply`, `swap_apply`, `power_apply`, `kpart_write`, `partition_write`, and
    `profile_*` (the passphrase is the person's). A call to one is an error that names the
    menu to point the person at.
- **The manifest**: `lazyos mcp --tools` prints the same table the server serves (one source),
  with tier, input schema hash and the subcommand it maps to, under a manifest version (a hash
  of the whole table). A pinned version in the instructions file must match it.
- **Registration**: `~/.config/opencode/opencode.json` gains the local MCP entry
  (`"type": "local"`, command `["lazyos", "mcp"]`), shipped by the image; the instructions are
  `~/.config/opencode/AGENTS.md`, the global rules file OpenCode reads in every session, and
  carry the pinned manifest version.
- **Resources**: the manual pages (`usr/share/doc/lazyos/*.md`) and the active theme, so the
  AI reads the same documentation the person does.

**Out:** chat with streaming (spec 013+), the vision loop over `desktop_screenshot` (a later
tier), any apply-level tool, and `task_start`: no task is *declared* startable yet (the
declarations arrive with the pickers of spec 010), so a start tool would have nothing to start;
it lands with them.

## Design

- The tier is **data**, not a comment: `ToolSpec { name, tier, schema, command }`; the
  `tools/list` response is generated from it, and a tool whose tier is `Refuse` is rejected at
  build time (a `const` assertion over the table, plus a unit test that iterates it).
- A propose tool is a door, not a second gate: it starts the same program the menu row starts,
  so the confirmation a person already knows - Cancel first, the disk's name typed, the second
  answer - is the only path to the apply command, which lives in that program, not in MCP.
- The protocol is hand-written in `lazyos-mcp` (newline-delimited JSON-RPC, a dozen methods,
  `serde_json` already in the tree) rather than the plan's `rmcp`, which brings an async
  runtime and a schema derive for a server that reads one line at a time; the crate holds the
  protocol, the table and the argument validator, and `lazyos-cli` implements the effects, so
  every tool runs the program the menus run.
- Every tool call is logged to `~/.local/state/lazyos/mcp.log` (name, tier, outcome, elapsed,
  never the arguments) for the person and for the check.
- The screenshot tool takes a temp path under `$XDG_RUNTIME_DIR` (0600, in a directory of the
  server's own) and deletes it on exit - on end of input and on SIGTERM/SIGINT/SIGHUP; it never
  writes into `$HOME`, keeps at most four, and a later server sweeps a directory whose owner
  died.
- stdio only: the server exits with the client, so nothing stays resident.

## Acceptance criteria

- [ ] `lazyos mcp --tools` lists every tool with its tier; no `refuse` name appears; every
      `act` tool maps to a real subcommand (test: the mapping resolves).
- [ ] `initialize` + `tools/list` over a pipe returns the same table; `tools/call` on a read
      tool returns data; on a propose tool returns "proposed" and the gated window opens.
- [ ] a call to a name not in the manifest (e.g. `format_apply`) is answered with an error and
      the refusal is logged; the process stays alive.
- [ ] `opencode.json` registers the server and an `opencode` session lists the tools; the
      instructions file's pinned manifest version equals `--tools`' version.
- [ ] a screenshot call leaves no file behind after the client disconnects.
- [ ] witness: `scripts/check-system.sh` FAILs when the `mcp` entry is missing from
      `opencode.json`, when `--tools` exits non-zero, when a `refuse`-tier name is listed,
      when the instructions version differs, and when a `propose` tool has no corresponding
      gated window.
- [ ] witness: a paragraph in `uis/sway/files/usr/share/doc/lazyos/07-agents.md`
      § *The desktop the agent can drive* lists the tiers and what the AI can and cannot do.
- [ ] witness: an `AGENTS.md` bullet says the manifest is the witness and apply-level tools are
      never exposed.
- [ ] unit tests: manifest snapshot, `refuse_never_listed`, `every_act_has_a_subcommand`,
      JSON-RPC framing (requests, notifications, errors), schema validation of a bad call,
      temp-file cleanup on disconnect.

## Tests

- **Unit** (`cargo test`): manifest/table consistency, tier filtering, JSON-RPC encode/decode, error codes.
- **Snapshot**: the Power confirm `power_propose` opens (Cancel selected), the one gated window
  this repository draws; Format's gate is `rofi-format`'s own list and stays as it is.
- **Integration**: spawn the server, run a scripted session over stdio (init, list, call,
  bad call, disconnect), assert the responses and the log lines.
- **Hardware**: an `opencode` session on the card asks for status, takes a screenshot, proposes
  a power off (and the person cancels); nothing changes on the machine.

## Risks

- **A tool that maps to a shell string** — the mapping is an enum; a test forbids `sh -c`.
- **The screenshot path leaks a private window into a temp file** — the file is 0600 under
  `$XDG_RUNTIME_DIR` and removed on exit; the manual states that a screenshot is what the AI
  sees.
- **A propose tool used as a nuisance** — an agent in a loop could open the Power confirm over
  and over; each propose tool has a cooldown and says so instead of opening a second window.
