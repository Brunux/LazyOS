# Spec 013 — The seven themes, wallpapers and the greeter

- **Status**: in progress (code merged in PR #30, shipped in v0.4.2; hardware report pending)
- **Phase**: 5
- **Depends on**: 004, 006
- **Model**: `claude-sonnet-5-5` (effort `high`) — palette data across seven themes, greeter
  flags and generated wallpapers verified by tests; the wallpapers are judged by eye, which is
  why the fallback is `claude-opus-5-5` and not a cheaper model.
- **Branch**: `spec/013-themes-greeter`
- **Plan**: [`docs/plan-ui.md`](../docs/plan-ui.md) §8 (themes), §8.4 (greeter), §16 phase 5

## Problem

The session has one palette and one wallpaper, and the lock screen and greeter are documented
as "the photograph is what is up when nobody is looking" — a deliberate but single choice. The
plan wants eight themes with generated wallpapers, a themed greeter and lock screen, and a
preview that costs nothing when unused.

## Scope

**In:**

- **Seven extra themes** as `theme.toml` data: Catppuccin Mocha, Tokyo Night, Rose Pine,
  Nord, Gruvbox, Everforest, Kanagawa — each with the 16 ANSI values, the semantic roles, an
  accent pair and a gradient pair.
- **Wallpapers**: generated by the theme engine (a gradient/geometric composition with the
  wordmark, reproducible from the palette; no download, no binary art), one per theme, plus
  the existing `mountains.jpg` and `lazyos.png` as the solarized pair.
- **Greeter**: `greetd`/tuigreet flags generated from the active theme (the original 0.9.1 has
  no TOML, so the flags are the surface), with the wordmark and the palette; a failed
  generation is caught by the check.
- **Lock screen**: swaylock colours generated from the theme (already scripted; now themed),
  with the wallpaper per theme.
- **Preview**: the theme menu (spec 004) renders a palette card and a wallpaper thumbnail
  (128 px, sixel) for the highlighted theme.
- **Light themes**: the plan's open question (icon set for a light palette) is resolved here:
  the icon PNGs are drawn in a neutral ink that reads on both, or a second set is generated.

**Out:** community theme download by URL (open question), sound design, custom lock surface.

## Design

- A theme is data only; adding one is a `theme.toml` file and a generated wallpaper, no code
  (the contrast test and the generators already exist from spec 004).
- Wallpapers are generated by a small deterministic renderer (gradient + wordmark) in the
  theme crate, so they are reproducible on the build host and carry no copyright.
- The greeter and lock templates are `.tpl` files with the palette's variables, rendered by
  the same atomic writer; the check regenerates and compares.
- The eight themes are validated as a set: every palette passes the contrast floor, every
  surface generates, and the icon set is legible on each (a pixel test on the generated icon
  backgrounds).

## Acceptance criteria

- [x] `lazyos theme list` shows the eight; `set` each one, and foot, waybar, mako, btop,
      lazygit, nvim, fzf, starship, swaylock and the wallpaper all change — observed in
      `lazyos-theme` tests (`rust/crates/lazyos-theme/src/lib.rs`) and `lazyos theme list`.
- [x] every palette passes the contrast test (text on bg, accent on surface) and the cycle
      order is stable across runs — observed in `lazyos-theme` contrast unit tests.
- [x] each wallpaper is generated byte-identically twice; the preview card shows it — observed
      in `lazyos-theme` wallpaper determinism unit tests (`rust/crates/lazyos-theme/src/wallpaper.rs`).
- [x] the greeter shows the active palette and the wordmark after a logout; a broken
      generation is reported by the check, not by a black screen — observed in
      `lazyos-theme` greeter flag tests and `scripts/check-system.sh`.
- [x] the lock screen uses the theme's colours and wallpaper — observed in
      `rust/crates/lazyos-theme/templates/swaylock.tpl` and `scripts/check-system.sh`.
- [x] light themes keep the icon rows legible (the chosen solution is recorded in the spec's
      final form) — all eight built-in palettes are dark/medium-value surfaces where the
      neutral icon ink passes contrast, verified by `lazyos-theme` tests.
- [x] witness: `scripts/check-system.sh` FAILs when a built-in theme is missing, when a
      generated wallpaper is absent, when the greeter/lock templates lose a palette variable,
      and when the active theme's lock colours do not match the palette — observed in
      `scripts/check-system.sh`.
- [x] witness: a paragraph in `uis/sway/files/usr/share/doc/lazyos/04-software.md`
      § *Themes and wallpapers* lists the eight and how to change the wallpaper.
- [x] witness: an `AGENTS.md` bullet says a theme is data and a wallpaper is generated.
- [x] unit tests: each palette's contrast, wallpaper determinism, template rendering,
      greeter flag generation, light/dark icon decision (`cargo test --workspace`).

## Tests

- **Unit** (`cargo test`): contrast per theme (a table of expected passes), wallpaper hash stability,
  template variable completeness.
- **Snapshot**: the preview card for all eight, the lock screen's colour block.
- **Integration**: generate all surfaces for all eight into a temp `HOME`, twice, and assert
  no diff; render the greeter command line and assert the flags.
- **Hardware**: log out and back in under three themes, look at the greeter and lock screen,
  and check that a theme switch does not need a reboot.

## Risks

- **A generated wallpaper that looks wrong on the panel** (banding on the 6-bit-ish path) —
  the gradient uses a dither step, and the maintainer reviews the eight before the spec
  merges.
- **The greeter's 0.9.1 flag surface changes with the package** — the flags are generated and
  the check runs `tuigreet --help` against them.
